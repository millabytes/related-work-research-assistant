# Related Work Research Assistant

Related Work Research Assistant is a local prototype for exploring scientific literature. It
works with an ingested collection of PDFs, recommends papers related to a selected article,
shows the evidence behind those recommendations, and drafts a Related Work section.

The project produces:

- structured metadata and full text;
- section-aware chunks mapped back to PDF coordinates;
- semantically related paper recommendations;
- source-grounded chunk and sentence evidence;
- dynamically highlighted PDF pages;
- citation-aware Related Work drafts generated by PRIMERA, Qwen, or Qwen + LoRA;
- reproducible benchmark and evidence-grounding evaluations.

The application follows an API-first architecture, with **FastAPI** serving as the backend for paper recommendations, generation requests, job status tracking, and result retrieval. Long-running generation tasks are handled asynchronously by a background worker, with PostgreSQL storing job states and results.

**Streamlit** provides a lightweight interactive frontend for exploring recommended papers, highlighting relevant passages in PDFs, generating Related Work sections, and comparing model evaluations.

## What was implemented

The implemented pipeline is:

```text
PDF corpus
  -> PyMuPDF text and coordinates
  -> GROBID metadata and structured TEI
  -> section-aware chunks with PDF source mapping
  -> SPECTER2 paper embeddings + BGE chunk embeddings
  -> top-k paper recommendations
  -> BGE chunk candidates
  -> MiniLM chunk reranking
  -> BGE + MiniLM sentence evidence
  -> PDF highlighting
  -> PRIMERA / Qwen / Qwen LoRA generation
  -> ROUGE and evidence-grounding evaluation
```

The system stores model and prompt versions, retrieval evidence, and generation results to inspect outputs, debug failures, and compare different runs.
Generated prose is associated with the exact evidence snapshot supplied to the model.

## Why these components?

**SPECTER2 for paper recommendations.** Its scientific-document embeddings represent a paper
using its title and abstract, making it suitable for finding related research at the paper
level. Searching these smaller representations is also cheaper than comparing the full text of
every paper.

**BGE and MiniLM for evidence.** Once relevant papers are selected, the task changes: we need
to locate specific supporting passages. BGE embeddings efficiently shortlist semantically
similar chunks and sentences. A MiniLM Cross-Encoder then scores the smaller candidate set
more precisely using both texts together.

**PRIMERA, Qwen, and LoRA for generation.** PRIMERA is a useful scientific summarization
baseline because it was adapted to Multi-XScience and accepts sets of paper abstracts. Its
checkpoint does not reliably attribute claims to individual citation IDs. Qwen2.5-0.5B-Instruct
is a small instruction-following alternative that can receive explicit evidence passages and
short citation IDs. LoRA adapts Qwen to the Related Work task using human-written Multi-XScience
examples while updating a small set of additional parameters rather than the whole model. The
base Qwen and LoRA variants use the same production input, so their outputs can be compared
without changing the retrieved evidence.

**FastAPI and Streamlit for the application.** FastAPI keeps retrieval and generation behind a
backend that can also be used by other clients. Streamlit was chosen as a quick way to build an
interactive research/demo interface, rather than spending time on a custom frontend. The
background worker keeps model inference separate from HTTP requests and UI refreshes.

## Quick review without private data

The repository contains the source code and automated tests, but not the original PDF corpus or downloaded model weights. Unit tests use small test fixtures or mocks and can be run independently of the full application. Running the complete pipeline requires a local PDF collection, PostgreSQL, GROBID, and the corresponding ML models.


## End-to-end local setup

### 1. Requirements

- Python 3.12
- [uv](https://docs.astral.sh/uv/)
- Docker with Compose
- enough disk space for PDFs and model checkpoints :(

```bash
uv sync --locked
cp .env.example .env
```

Set a local `POSTGRES_PASSWORD` in `.env`.

### 2. Start PostgreSQL and GROBID

```bash
docker compose up -d --wait db
docker compose --profile extraction up -d --wait grobid

uv run alembic upgrade head
uv run related-work db-check
```

PostgreSQL stores metadata, chunks, embeddings, generation jobs, and outputs. GROBID extracts
scientific metadata and structured full text from the original PDFs.

### 3. Add input documents

For this prototype, the document corpus was assembled by exporting PDFs from **several Zotero
collections**. We also exported Zotero bibliographic metadata separately. The PDFs are the
actual input to document extraction; **GROBID independently extracts metadata from each PDF**.
The Zotero export serves as reference (*ground-truth*) metadata for checking the quality of
that extraction, not as metadata fed into GROBID or used to silently correct its results.

Place the exported PDFs anywhere below:

```text
data/raw_data/papers/
```

Nested directories are supported, so separate Zotero collections can remain in their own
folders. If you want to evaluate extracted metadata, put the Zotero RDF export at
`data/raw_data/zotero_metadata.rdf`. This reference file is optional for running the assistant.

**How the input works:** the current Streamlit interface lets you select a paper **already
ingested into PostgreSQL**. It does not currently provide an arbitrary-PDF upload workflow.
To analyse a new PDF, add it to the corpus, run ingestion, chunking, and embeddings, then select
it in the UI. Two or three PDFs are enough to inspect extraction and chunking; five related
recommendations require at least six eligible papers in the database.

### 4. Ingest a small sample

```bash
uv run related-work ingest data/raw_data/papers --limit 3
```

For every original PDF:

- PyMuPDF extracts page text, blocks, words, and bounding boxes.
- GROBID extracts title, authors, abstract, year, venue, DOI, and keywords.

GROBID reads the PDF itself, not PyMuPDF output. Their normalized text and positions are stored
separately and are not assumed to be identical.

```bash
uv run related-work show-metadata PAPER_UUID

# Optional, when Zotero RDF is available:
uv run related-work evaluate-metadata
```

### 5. Extract structured full text and create chunks

```bash
uv run related-work chunk data/raw_data/papers --limit 3
```

This calls GROBID `processFulltextDocument` with sentence segmentation and TEI coordinates.
The TEI response is cached under `data/processed/`.

Chunks:

- never cross section boundaries;
- target 200–400 tokens;
- combine short paragraphs inside a section;
- split long paragraphs at sentence boundaries;
- exclude bibliographies and technical page labels;
- retain page ranges and sentence-level PDF mappings.

After checking the sample:

```bash
uv run related-work chunk data/raw_data/papers
```

### 6. Generate embeddings

```bash
uv run related-work embed-papers --batch-size 8 --device auto
uv run related-work embed-chunks --batch-size 32 --device auto
uv run related-work embeddings-status
```

- Paper embeddings use `allenai/specter2_base` with the `allenai/specter2` adapter over
  GROBID title + abstract. Dimension: 768.
- Chunk embeddings use `BAAI/bge-small-en-v1.5`. Dimension: 384.

The first run downloads weights to `models_cache/huggingface/`. Inference already selects CUDA, MPS, or CPU. Input hashes and database constraints make unchanged reruns idempotent.

```bash
# Optional single-paper processing:
uv run related-work embed-papers --paper-id PAPER_UUID --device auto
uv run related-work embed-chunks --paper-id PAPER_UUID --device auto
```

### 7. Start the application

The FastAPI process exposes the backend endpoints; Streamlit is the lightweight interface for
reviewing recommendations, PDF evidence, generations, and saved evaluation results. Use three
terminals to run the backend, background worker, and UI separately.

Terminal 1 — FastAPI:

```bash
uv run uvicorn related_work_assistant.api.main:app --reload
```

Terminal 2 — background generation worker:

```bash
uv run related-work generation-worker
```

Terminal 3 — Streamlit:

```bash
uv run streamlit run streamlit_app.py
```

Open:

- Swagger: `http://127.0.0.1:8000/docs`
- Streamlit: normally `http://localhost:8501`

The API `paper_id` is the UUID returned by `GET /papers`; it is not a PDF hash.

## Minimal API walkthrough

```bash
# List selectable papers.
curl 'http://127.0.0.1:8000/papers?has_embedding=true&limit=100'

# Retrieve five papers and three reranked evidence pairs per paper.
curl 'http://127.0.0.1:8000/papers/PAPER_UUID/recommendations?top_k=5&chunk_candidates_per_paper=20&chunk_pairs_per_paper=3&rerank=true'

# Queue Qwen generation.
curl -X POST \
  'http://127.0.0.1:8000/papers/PAPER_UUID/related-work/generate' \
  -H 'Content-Type: application/json' \
  -d '{"models":["qwen"]}'

# Poll status and history.
curl 'http://127.0.0.1:8000/papers/PAPER_UUID/related-work?model=qwen'
```

Generation executes in the worker. Refreshing Swagger or Streamlit only reads PostgreSQL; it
does not start duplicate inference.

## Retrieval and evidence

### Paper retrieval

PostgreSQL/pgvector computes exact cosine distance between SPECTER2 paper embeddings. The query
paper is excluded. Year and venue filters are applied before ranking and limiting the result
count. Only matching model versions are compared.

### Chunk and sentence retrieval

BGE first returns a configurable chunk-pair candidate pool.
`cross-encoder/ms-marco-MiniLM-L6-v2` reranks the candidates. Responses preserve both BGE
similarity and Cross-Encoder score. Set `rerank=false` for the BGE-only baseline.

For final evidence, the system uses original GROBID sentences, BGE sentence similarity, and
MiniLM sentence reranking. Only validated PyMuPDF mappings receive PDF coordinates.

Streamlit displays both PDFs side by side and renders temporary, color-matched annotations in
memory. Original PDFs are never modified.

## Related Work generation

All generators use durable PostgreSQL jobs. Outputs, errors, token counts, finish reasons, model
revisions, prompts, and evidence snapshots are preserved as versioned history.

### PRIMERA

`allenai/PRIMERA-multixscience` receives the target abstract and five related abstracts joined with `<doc-sep>`. We use it as a baseline because it was specifically trained for scientific multi-document summarization, not an instruction-tuned citation generator. However, its outputs often contain generic cite placeholders rather than references to specific papers, making citation attribution difficult. This limitation motivated us to also explore Qwen2.5-0.5B-Instruct, which allows us to explicitly specify citation identifiers in the prompt and validate them against the retrieved papers.


### Qwen

`Qwen/Qwen2.5-0.5B-Instruct` receives:

- target title and abstract;
- five recommended papers with `[R1]`–`[R5]` identifiers;
- each recommended title and abstract;
- three complete MiniLM-reranked chunk pairs per recommendation.

Short citation IDs are mapped deterministically to persistent citation keys. Unknown citations,
UUIDs, internal markers, headings/lists, repetition, and incomplete length-limited outputs fail
validation instead of appearing as completed results.

### Qwen LoRA

`qwen_lora` receives exactly the same production prompt and evidence snapshot as base Qwen.
Only the trained adapter changes. Without a validated adapter, the API reports the model as
unavailable.

```bash
uv run related-work regenerate-qwen --all
uv run related-work qwen-status

uv run related-work regenerate-qwen-lora --all
uv run related-work qwen-lora-generation-status
```

Run only one `generation-worker` process to avoid competing model copies.

## Multi-XScience preparation

```bash
uv run related-work prepare-multixscience
```

Preprocessing preserves official splits and maps `@cite_N` to deterministic `[R1]`, `[R2]`,
... identifiers. The user message contains only target and reference abstracts; the human
Related Work target appears only in the assistant message.

| Split | Valid examples |
|---|---:|
| Train | 19,337 |
| Validation | 3,230 |
| Test | 3,209 |

Ungroundable citations remain in an invalid audit instead of receiving invented mappings.

```bash
uv run related-work inspect-multixscience --split train --limit 2
uv run related-work analyze-multixscience-invalid
```

## Qwen LoRA training

PEFT LoRA training computes loss only over assistant tokens. Validation loss selects
checkpoints; the test split is never used for training or hyperparameter selection.

```bash
# Smoke test.
uv run related-work train-qwen-lora-smoke \
  --train-limit 8 \
  --validation-limit 4 \
  --max-steps 2 \
  --device auto

# Full training.
uv run related-work train-qwen-lora \
  --epochs 3 \
  --batch-size 1 \
  --gradient-accumulation 16 \
  --mixed-precision auto \
  --device auto

# Resume and inspect.
uv run related-work train-qwen-lora --resume latest --device auto
uv run related-work qwen-lora-training-status
```

The production adapter activates only after its manifest, base revision, and fingerprint
validate successfully.

## Evaluation

The project has two complementary evaluations. **Both assess generated Related Work text**, but
answer different questions. They run explicitly via the CLI; Streamlit displays saved results
in the evaluation section below Related Work Generation. This README describes the evaluation methods, not their
scores.

### Evaluation A — held-out Multi-XScience benchmark

**Question:** how closely does a generated Related Work passage match a human-written one?

### Evaluation A — Multi-XScience benchmark

**Question:** How well do the models generate Related Work compared to human-written references?

This evaluation uses the Multi-XScience test set, which contains target-paper abstracts, referenced-paper abstracts, and human-written Related Work passages.

Unlike our production pipeline, where Qwen also receives retrieved evidence chunks, this benchmark uses only abstracts for all three models. PRIMERA uses its original `<doc-sep>` format, while Qwen and Qwen + LoRA use a citation-aware prompt.

We compare the generated Related Work passages against the human-written references using ROUGE-1, ROUGE-2, and ROUGE-L F1. Both per-example scores and aggregate metrics are saved, together with sample IDs, model revisions, and evaluation settings. These metrics measure textual similarity to the reference passages, rather than factual correctness.

The models' production prompts remain unchanged. The complete generation pipeline, including retrieved evidence chunks for Qwen, is evaluated separately in Evaluation B.


```bash
uv run related-work evaluate-generation-a --limit 10 --seed 42 --device auto
uv run related-work evaluate-generation-a --full --seed 42 --device auto
```

### Evaluation B — production evidence grounding

**Question:** are the citations and claims in the application-generated Related Work drafts
supported by the retrieved papers?

This evaluation uses papers in the local PostgreSQL corpus, existing generated outputs, and the
retrieval evidence snapshots saved with them. There is no human-written reference for the exact
set of five papers recommended by the system, so ROUGE is not the right measure here.

Each model keeps its **normal production input**: PRIMERA receives abstracts; Qwen and Qwen +
LoRA receive titles, abstracts, and reranked evidence chunk pairs. Metrics include citation
validity (whether cited IDs resolve to allowed papers), citation coverage (how many recommended
papers are cited, without treating 100% as a goal), and source-constrained NLI scores estimating
whether individual claims are supported, neutral, or contradicted by evidence from the cited
paper. Generic PRIMERA `cite` placeholders cannot be assigned to specific sources and are
reported as unresolved. Recorded inference latency and peak memory are shown where available;
cached outputs are not treated as new inference measurements.

NLI is an approximate grounding check, not proof of scientific truth. Because PRIMERA gets less
source material than the Qwen variants, Evaluation B compares the **deployed generation
pipelines**, not three models under identical input conditions. The direct Qwen versus Qwen +
LoRA comparison does use the same evidence snapshot.

```bash
uv run related-work evaluate-generation-b PAPER_UUID --device auto
uv run related-work evaluate-generation-b-fixed --limit 10 --seed 42 --device auto

uv run related-work generation-evaluation-results --kind a --limit 5
uv run related-work generation-evaluation-results --kind b --limit 5
```

## Database and reproducibility

Alembic is the only schema bootstrap mechanism:

```bash
uv run alembic upgrade head
uv run alembic current
```

The schema separates papers, files, authors, sections, chunks, model versions, embeddings,
generation jobs, and generation results. Reproducibility fields include immutable revisions,
pipeline and prompt versions, content/input/evidence hashes, exact evidence snapshots, token
counts, finish reasons, validation errors, latency, and available peak-memory measurements.

Unchanged reruns are idempotent. Forced generation creates new history instead of deleting old
outputs.

## Known limitations

- Retrieval searches only the locally ingested corpus.
- GROBID and PyMuPDF text may differ; only validated mappings are highlighted.
- PRIMERA is a summarization baseline rather than a citation-aware instruction model.
- NLI scores approximate evidence support and do not establish scientific truth.
- The generation worker is sequential to keep memory usage predictable.
- Full-corpus processing and full benchmark evaluation require substantial time and storage.

## Backup

PostgreSQL stores metadata, chunks, embeddings, and generation history, but not PDF bytes.

```bash
docker compose exec -T db \
  pg_dump -U related_work -d related_work -Fc \
  > related_work.dump
```

`docker compose down` preserves the volume. `docker compose down -v` deletes it.
